## 0. 한 문장

**고정된 커널 위에, 타입이 선언된 구성요소로 이루어진 하네스를 얹고, 하네스는 RRSI 로(무엇을 바꾸고 남길지), 탐색 정책은 Dream-RSI 로(계산을 어디에 쓸지) 진화시키되, 모든 변화는 기록·측정·재생 가능하고 기존 I/O 계약 아래에서 갈아끼울 수 있게 한다.**

## 2. 원칙 (P1–P12)

### P1. 커널은 고정, 하네스는 진화 (정책 π 처럼)

RRSI 에서 π 는 고정이고 H 만 진화한다. 우리는 한 단계 더 나눠 **커널 K₀ 도 고정**한다.

```
실행 에이전트  A = (π, K₀, H, π_E)
  π   : 고정 정책(공급자+모델, 대화·노드 입력이 고름)
  K₀  : 고정 커널(이 문서 §3 목록) — 진화 금지, 사람만 바꿈
  H   : 하네스(𝒦 9종 구성요소) — RRSI 가 진화
  π_E : 탐색 정책 — Dream-RSI 가 진화
```

근거: RRSI 헌법 hard rule 3·5("검증기를 건드리지 마라", "계약을 깨지 마라, 모델·스텝 예산·타임아웃은 외부 주입")를 **구조로** 보장하려면 검증·계측·계약·한도가 하네스 밖에 있어야 한다. 하네스 코드가 손댈 수 없는 곳에 있으면 critic 이 놓쳐도 게이밍이 불가능하다.

### P2. 하네스의 모든 것은 정확히 하나의 구성요소에 속하고, 구성요소는 𝒦 타입을 선언한다

- 𝒦 = {prompt, control_flow, config, output_plumbing, context_mgmt, client_tool, skill, memory, subagent} — **RRSI 어휘를 그대로**(수식 Eq.12/15/16 보존).
- 하네스 버전은 구성요소 manifest + 파일들의 **내용 주소(트리 해시)** 다. RRSI 의 "incumbent 는 항상 commit" 과 기존 런타임의 "Configuration is artifact" 가 같은 것이 된다.
- 태그 검증이 정규식 추측이 아니라 **타입 선언 대조**가 된다(02 문서 D10). 편집 diff 가 건드린 파일의 선언 kind 가 곧 ℓ 이다.
- 기존 `harness_components.py` 의 관측 카운터(13 문서 §2)는 구성요소별 발화 계측으로 승계한다(usage.harness 계약 유지).

### P3. 세 층의 합성: 진화 하네스 ⊕ 에이전트 설정 ⊕ 세션 overlay

```
실행 하네스(turn) = H*(lineage(π))  ⊕  에이전트 설정(입력 x: 노드 지침·도구·스킬·메모리 설정)  ⊕  세션 overlay(env 식 자기 수정)
```

- RRSI 가 진화시키는 것은 **H\*** 뿐이다. 에이전트 설정은 태스크 입력이고(사용자가 쓴 지침·고른 도구), 세션 overlay 는 대화 안의 일시 변경이다.
- H\* 는 모든 에이전트 설정에 대해 **일반적**이어야 한다. RRSI 리트머스 "같은 종류의 다른 스위트의 낯선 태스크에서도 도움이 되는가"를 "**다른 고객의 다른 에이전트에서도 도움이 되는가**"로 옮긴다.
- 합성 우선순위(충돌 시): 커널 한도 > 에이전트 설정의 명시 값 > 세션 overlay > H\* 기본값. (기존 5단계 우선순위 10 문서 §1.3 의 정신을 단순화)

### P4. 측정은 커널의 의무이고, 하네스는 측정을 볼 수도 바꿀 수도 없다

- c(τ) = 정책 π 에 대한 **모든** 호출(메인 루프, 압축 요약, 메모리 증류, 서브에이전트, 검증 패스)의 토큰 합. 커널의 단일 관문(Usage Ledger)에서만 계산한다. 12·13·14 문서가 찾은 누락(압축·증류·fork·재시도·CLI 내부 턴·reasoning)을 구조적으로 없앤다.
- r(x,τ) 는 오프라인 평가에서만 존재하고 하네스 실행 중에는 노출되지 않는다(채점기 게이밍 차단).
- 스텝 수, 유효 출력, 미제출, 종료 사유도 커널이 기록한다.
- 기존 usage 페이로드 계약(anthropic·bedrock 캐시 비대칭 포함, 11 문서 §3.5)은 **출력 어댑터에서 그대로** 만든다. 내부 원장은 더 정밀하고, 외부 표현은 기존과 같다.

### P5. 블록 좌표 상승 — H 와 π_E 는 번갈아, 소유권을 나눠 진화

- 탐색 정책은 RRSI 어휘로는 control_flow 지만, 두 루프가 같은 코드를 동시에 바꾸면 ΔS 귀속이 깨진다.
- **RRSI 실행 중 π_E 고정, Dream 사이클 중 H 고정.** π_E 파일은 RRSI proposer 의 편집 가능 경로에서 제외(소유권 = Dream 루프).
- 수학적 해석: 목적 J(H, π_E) 에 대한 좌표별 개선. RRSI 단계는 J(·, π_E) 를 정규화된 방식으로, Dream 단계는 J(H, ·) 를 재생으로 올린다. 두 단계 모두 "현재 해 포함 argmax"(RRSI: 허용 후보 없으면 H_t 유지, Dream: π^0 포함)라 각자의 측정 위에서 퇴보하지 않는다.

### P6. 탐색은 검증 가능한 곳에서만 분기한다

- Dream-RSI 의 s_v 는 평가기 점수다. 턴 안에서 자동 검증기가 있는 하위 작업(샌드박스 코드+테스트, 실행으로 확인되는 질의, 스키마·린트로 검증되는 산출물, 결정적 종료 상태가 있는 도구 작업)에서만 branch × attempt 탐색을 연다.
- 검증기가 없는 턴은 **퇴화 트리**(가지 1, 정련 = 일반 에이전트 루프). 기존 동작과 같아 I/O·비용이 변하지 않는다.
- 탐색의 병렬 시도는 c(τ) 를 늘린다 → RRSI 비용 규칙과 Dream Eq.1 의 −β1·N 이 함께 억제한다.

### P7. 진화가 세계를 공급하고, 세계가 진화를 싸게 한다

- RRSI 후보 평가(evolve 집합 × k 실행)가 남기는 모든 시행 기록은 그대로 Dream 의 재생 세계다(태스크별 트리). 온라인 운영의 검증 가능 턴도 세계를 공급한다(개인정보 정책 허용 시, §5).
- RRSI 평가의 **정확 경계 조기 종료**: 후보의 남은 시행이 전부 r=1 이어도 `Ŝ' < S★ − δ` 면 평가를 멈춘다. 판정이 수학적으로 바뀌지 않으므로 무위험 절감(33 문서에 정식화).
- Dream 이 학습하는 **평가 할당 정책**(통계적 조기 종료, 후보 수 m_t 조절)은 RRSI 판정을 바꿀 수 있으므로 별도 실험 단계(PLAN Phase 9)로 둔다.

### P8. 하네스 계보는 정책 계열별

- 사용자는 대화마다 모델을 고른다(다중 공급자 유지가 요구사항). RRSI 는 정책별로 진화했다(Table 3).
- `lineage: (provider, model_family) → H 버전`. 미등록 정책은 **기본 계보**로 fallback(Table 4 의 교차 모델 이전이 근거).
- 루프를 소유하는 공급자(Claude Code CLI, Codex CLI)는 하네스가 control_flow 를 통제할 수 없다(12 문서 §3.9). 이 계보에서는 편집 가능 𝒦 가 줄어든다(prompt, config, client_tool, skill, memory, context_mgmt 의 턴 전 부분). control_flow 편집은 "비활성 기계장치"로 critic 규칙 2 에 걸린다.

### P9. 운영 반영은 RRSI 게이트 + 사람 승인

- 운영 H\*·π_E\* 변경은 (1) RRSI 선택 규칙 전체(누설 심사, 바닥, 비용/대역 규칙, 가드) → (2) held-out 확인(진화 루프 밖, 판정에 쓰지 않음, 보고 전용) → (3) **사람 승인**(MR/PR 리뷰·머지) → (4) 단계 배포(shadow → canary → 기본).
- π_E 는 재생 선택(V^{m★} ≥ V^0) 뒤에 **RRSI 식 온라인 확인**(바닥 + 비용 규칙)을 한 번 더 통과해야 승격된다. 재생은 관측된 공간만 보므로, 새 방향의 위험을 RRSI 의 보수적 선택이 막는다.

### P10. 이력은 증거이자 세계 — 두 용도를 섞지 않는다

- RRSI 의 𝓛_t(편집 가설의 측정 기록)는 proposer 의 조건 정보다.
- Dream 의 𝓗_t(발견 트리)는 정책을 실행해 보는 시뮬레이터다.
- Dream §5.1 의 경고("이력을 방향 지침으로 프롬프트에 넣으면 탐색 다양성이 줄어든다")에 따라, **턴 안의 탐색 에이전트에는 이력 요약 지침을 주입하지 않는다**. 원자료 열람(B.1 방식)과 direction provider 의 구조 태그로 다양성을 보장한다. 하네스 진화 proposer 에는 RRSI 방식 그대로 이력·보고서를 준다(층위가 다르다, 20 문서 §4.4).

### P11. 수식은 순수 함수, 판정은 재현 가능

- 05 문서의 모든 식은 부작용 없는 순수 함수로 구현하고, 판정 입력 전체를 함께 저장해 **재판정(readjudicate)** 이 언제나 가능해야 한다.
- 공식 RRSI 구현과의 **차분 테스트**(같은 입력 → 같은 출력)로 수식 정확성을 기계적으로 증명한다.

### P12. 문서는 코드에서 나온다

- 10·13 문서가 찾은 문서-코드 불일치(9건 이상)를 반복하지 않도록, 구성요소 manifest·이벤트 카탈로그·계약 표가 문서의 원천이 되고 문서는 생성물로 둔다.

### 3.2 하네스(진화 대상, 𝒦 타입)

| ℓ | 무엇이 들어가나 (기존 출처 → 13 문서) |
|---|---|
| prompt | 시스템 프롬프트 블록(`_constants.py` 블록들, Stage 3 블록), 도구 설명 재정의, 완료 게이트 문구, 이어가기/안내 문구 중 모델이 보는 것 |
| control_flow | 턴 제어 프로그램(언제 계획·행동·검증·정지), 완료 판정 규칙, 반복 가드, 산출물 점검(`DeliverableReviewer`), 복구 정책 — **π_E 제외**(Dream 소유) |

| context_mgmt | prune, 요약 압축(트리거·목표·프롬프트), 입력 예산 맞추기 정책, 고정 블록 보호, 메모리 주입 예산 |
| client_tool | 노출 정책(턴1 표면, 문→가족, ToolSearch 숨김 목록), 하네스 측 도구(host-side callable), 도구 등록(ForgeTool 식 사전 실행 게이트 필수) |
| skill | Guide 문 + 가족, SKILL.md 스킬(점진 공개), 통합 `SkillSpec` |
| memory | 메모리 정책(주입 예산, 층 비율, 노출 도구, 증류 스펙·주기). **기억 내용 자체는 H 가 아님**(사용자 데이터) |
| subagent | 같은 정책에 대한 제한된 추가 호출(검증·요약·계획 brief). **플랫폼 결정("다시 들이지 않는다", 13 문서 §3.9)과 충돌 → 결정 필요(PLAN §결정 D-3)** |

### 3.3 탐색 정책 π_E (Dream 소유)

`OptimalPolicy`(B.2 API) 형태의 순수 Python 정책 + `plan_grid` + β 기본값. 커널의 탐색 실행기가 호출한다. RRSI 실행 중에는 고정.

## 4. 세 루프

```
L0  온라인 턴 실행        : 커널 + H*(lineage) + π_E*  → 기존 I/O 계약 그대로, 모든 실행 = 트리
L1  RRSI 하네스 진화      : D_evolve 에서 Algorithm 1·2, π_E 고정 → H 후보 → 게이트 → 승인 → H*
L2  Dream 탐색 정책 진화  : 세계 풀(L1 시행 기록 + 허용된 L0 기록) 재생 → π^0..π^{M−1} → argmax V → 온라인 확인 → 승인 → π_E*
(L1') Dream over L1 제어기 : RRSI 의 평가 할당(조기 종료·m_t)을 재생으로 학습 — 실험 단계
```

| | L0 | L1 | L2 |
|---|---|---|---|
| 주기 | 매 턴 | 운영 판단(예: 주 1회 또는 수동) | L1 사이 또는 세계 풀이 충분히 커졌을 때 |
| 비용 | 사용자 턴 비용 | 큼(후보 × |D| × k 실행 + 탐색 역할 LLM) | 작음(개발 에이전트 LLM + 재생 CPU) |
| 산출물 | 응답 + 트리 기록 | 하네스 버전(commit) + 𝓛_t + frontier | 정책 버전 + 재생 보고서 |
| 수식 | c(τ), (오프라인) r | Eq.3–17 | D-Eq.1, pareto.reward, β 규칙 |
| 실패 시 | 기존 오류 계약 | H_t 유지 | π_t 유지 |

## 6. 기존 21-stage 와 새 구조의 대응 (철학적 차이)

| 기존 | 새 구조 | 차이의 의미 |
|---|---|---|
| 21 칸 고정 번호, 칸마다 stage | 커널 + 𝒦 9종 구성요소 + π_E | "단계의 순서"가 아니라 "편집 단위의 종류"로 분해 → 원자 편집·귀속·가지치기가 성립 |
| `PipelineState` 공유 버스 | 커널 소유 불변 턴 스냅샷 + 타입 있는 구성요소 인터페이스 | 숨은 계약 제거, 구성요소를 독립적으로 바꿔도 안전 |
| 루프 결정 5곳 | control_flow 1곳 + 커널 한도 | 귀속 가능, 재생 가능 |
| `[COMPLETE]` 마커 | 구조적 완료 신호 + control_flow 규칙 | 프롬프트 편집이 완료 판정을 망가뜨리지 않음 |
| s14 evaluate(고정 점수) | 오프라인 검증기 r(x,τ) + 턴 내 검증 가능 하위 작업 | 진짜 품질 신호 |
| s07 비용(결함) | Usage Ledger 단일 관문 | c(τ) 정확 |
| `env` 도구(평가 없는 세션 자기 수정) | 세션 overlay(유지) + RRSI 전역 진화(평가·게이트) | 자기 수정을 두 층으로 분리 |
| ForgeTool 테스트 게이트 | client_tool 편집의 smoke 표준 | 기존 장치의 일반화 |
| rollout(관측 이벤트만) | 발견 트리(요청·응답·결과·스냅샷 참조) | 재생 가능 |
| 사람이 하네스 개선 | RRSI 제안 + 사람 승인 | 개선 속도는 기계, 책임은 사람 |

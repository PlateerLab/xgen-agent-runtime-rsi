# 34. 평가 체계 — 검증기, 평가 세트, 잡음 보정, 비용

> RRSI 의 모든 판정은 Ŝ, Ĉ, δ 에 달려 있고, Dream-RSI 의 세계는 점수 s_v 가 있어야 성립한다. 이 문서는 **무엇으로 재는가**를 정한다. 기존 관행은 [15-existing-methodology.md](../research/15-existing-methodology.md), 기록 현황은 [14](../research/14-runtime-observability-records.md).

## 1. 측정 계약 (커널이 τ 마다 산출)

| 신호 | 정의 | 산출 주체 | 판정 사용처 |
|---|---|---|---|
| r(x,τ) ∈ [0,1] | 검증기 보상 | 오프라인 Verifier (하네스 비가시) | Ŝ, s_v |
| w(x,τ) | 시행 가중치(criteria 수 등, 기본 1) | Verifier | Ŝ 가중 |
| c(τ) | 정책 토큰(모든 purpose 합) | Usage Ledger | Ĉ, ΔC |
| steps | model_calls, iterations, tool_calls, tool_errors | 커널 measure | 진단(Figure 4b) |
| valid_output | 산출물이 형식 요건을 만족(검증기 정의) | Verifier | 도메인 가드 |
| no_submission | 산출물 없음/완료 신호 없음 | 커널 + Verifier | 도메인 가드 |
| termination_reason | 기존 `TerminationReason` + 한도 종료 | 커널 | 진단 |
| missing | 크래시·타임아웃·인프라 | 평가 러너 | r=0 처리, 무효 게이트 |

- **검증기 인터페이스**

```python
class Verifier(Protocol):
    id: str; version: str
    def score(self, task: TaskSpec, artifact: ArtifactBundle, transcript: TranscriptView) -> VerifierResult: ...
@dataclass(frozen=True)
class VerifierResult:
    reward: float; weight: float = 1.0
    valid_output: bool | None = None; no_submission: bool | None = None
    criteria: tuple[CriterionVerdict, ...] = ()     # rubric 형이면 기준별 판정
    fail_class: str = "ok"; diagnostics: tuple[str, ...] = ()
```

- 검증기 종류: (a) **결정적**(unit test, 스키마/계약 검사, 질의 결과 비교, 파일 상태 비교) — 우선, (b) **rubric judge**(LLM-as-judge, 기준별 판정) — Harvey LAB 형.

### 1.1 judge 운용 규칙 (rubric 형)

1. judge 모델은 **XGEN 에 등록된 LLM 중 고정 1개·버전 고정**, 정책 π 와 **다른 계열**(자기 선호 편향 회피). 온도 0(또는 지원 최저).
2. 기준별(criterion) 판정, 시행 보상 = 통과 기준 수 / 전체, 가중치 = 전체 기준 수(RRSI workspace 방식).
3. 같은 산출물 해시 → 같은 판정 캐시(비용·일관성).
4. **judge drift 감시**: 고정 보정 세트(산출물 + 사람 판정)를 라운드마다 재채점, 일치율이 임계 아래로 떨어지면 라운드 무효.
5. judge 프롬프트·기준은 **하네스 밖**(커널/도메인 소유). 하네스가 judge 문구를 보거나 흉내 내는 편집은 critic 규칙 3(채점기 게이밍)으로 거부.

RRSI 는 "한 방법, 세 인스턴스"(코딩·workspace·엔지니어링)다. 우리도 인스턴스를 `EvalDomain` 으로 분리한다.

|---|---|---|---|---|---|---|---|
| **I-1** | Harness-Bench (Qihoo360) 실행 가능분 | 설계 38–39 | 홀드아웃 29–31 | I-2·I-3 일부 | 벤치 자체 채점(내용·형식) — 실험실 코드 확인 필요 | Qwen3.8-27B (기존 측정 연속성) | 기존 실험실 위치 미확인(D-8) |
| **I-2** | XGEN 업무 workspace (문서 검토·보고서·DB 질의 응답·RAG 근거 답변·파일 작업) | 신규 구축 ≥ 100 | ≥ 30 | 공개 벤치 부분집합(GDPval·JobBench 류, 라이선스 확인) | rubric judge + 결정적 계약 검사 혼합 | 운영 주력 모델(결정 D-4) | 구축 필요 |

- **I-1 을 첫 인스턴스로**: 기존 관행과 연속(기준선 다수 존재), 실험실 구조(실제 호스트 + 격리 컨테이너)가 RRSI 평가에 그대로 맞는다.

- 개인정보: I-2 는 **합성·허가 데이터**로만 구성. 운영 대화 원문은 쓰지 않는다(35 문서).

## 3. 잡음 대역 δ — 지금 규모로는 크다

### 3.1 기존 기록으로 본 개략 추정 (신뢰 낮음)

| 관측(15 문서) | 값 |
|---|---|
| 70과제 × 1시행, 같은 설정 2회 점수 | 0.847 · 0.807 (차 0.040) |
| 홀드아웃 31과제 × 1시행, 2회 | 0.844 · 0.783 (차 0.061) |

정규 근사에서 E|X−Y| ≈ 0.8·sd_null 이므로 sd_null ≈ 0.050 (70과제, k=1), 0.076 (31과제, k=1). 과제 수 n·시행 k 에 대해 sd_null ∝ 1/√(n·k) 로 근사하면:

| 세트 | k | sd_null(추정) | δ = 2·sd |
|---|---|---|---|
| 설계 39 | 1 | ≈ 0.067 | ≈ 0.13 |
| 설계 39 | 2 | ≈ 0.047 | ≈ 0.095 |
| 설계 39 | 4 | ≈ 0.034 | ≈ 0.067 |
| 70 전체 | 4 | ≈ 0.025 | ≈ 0.050 |
| 150 (보강 시) | 2 | ≈ 0.024 | ≈ 0.048 |
| 150 | 4 | ≈ 0.017 | ≈ 0.034 |

비교: RRSI 논문 δ = 0.017(178 시행), 0.020(244 시행), 0.004(약 14,100 criteria).

**해석**: 설계 39과제·k=2 이면 δ ≈ 0.1 이라, Eq.7 분기(ΔS > δ)에 들어가는 후보가 거의 없고 대부분 Eq.17(대역 안: 비용 절감·구조 새로움)로만 판정된다. 기존 관행에서 "점수 비열등 + 비용 감소" 로 채택하던 것과 같은 모양이지만, **품질 개선을 수용하는 능력은 거의 없다**. 대책:

1. **evolve 집합 확대**(I-1 + I-2 결합 또는 I-2 단독 ≥ 150) — 가장 효과적.
2. k 상향(비용 선형 증가).
3. criteria 형 채점(시행당 여러 판정 → 판정 단위 분산 감소, RRSI workspace 가 δ=0.004 인 이유).
4. 이 추정은 관측 2쌍 기반이라 **반드시 Phase 5 에서 R ≥ 3 base 평가로 실측 보정**(calibrate).

### 3.2 보정 절차 (Phase 5)

```
for r in 1..R (R ≥ 3):  Evaluate(H_0, D_evolve, k)       # 같은 하네스, 독립 실행
δ = calibrate([ev_1..ev_R], z = 2.0)                      # 05 문서 §2.4
+ 판정 단위별 분산 분해(과제 간 / 과제 내) 리포트 → k·|D| 선택 근거
```

## 5. 평가 러너 (EvalHost)

- **실제 엔진·실제 호스트 프로토콜**로 돈다: `RSITurnExecutor.run(EvalHost, **task_kwargs)`. EvalHost 는 `HostServices` 를 구현하는 평가 전용 호스트로, 격리 컨테이너(샌드박스)·고정 데이터(DB 스냅샷·파일 고정본)·결정적 도구 응답(필요 시)을 제공한다. 기존 실험실("실제 호스트·파이프라인 + 격리 컨테이너")과 같은 원칙.
- 태스크 = `{task_id, kwargs(에이전트 설정·입력), fixtures, verifier_id, weight}`. 에이전트 설정은 입력 x 의 일부(30 문서 P3).
- 병렬: 태스크 × 시행을 워커 풀로. 각 시행은 독립 샌드박스. 누락은 r=0.
- 재개 안전: 시행 단위 결과 파일, 재실행은 빠진 시행만(공식 코드 `domain.run` 규칙).
- 정확 경계 조기 종료(33 문서 §4) 옵션.
- 비용 계측: 정책 토큰(c), 탐색 역할 토큰(proposer/critic/analyst/digester/policy-dev/judge)을 **분리 집계**.

## 7. Dream-RSI 세계의 원천과 점수

| 원천 | 트리 모양 | s_v | 비고 |
|---|---|---|---|
| L1 평가 시행 | 태스크당 시행 k 개 = 루트에서 k 가지(각 가지 깊이 1) 또는 턴 안 탐색 격자 | r(x,τ) | 가장 큰 공급원. 같은 태스크·다른 하네스 버전의 세계가 쌓임 |
| 턴 안 탐색(검증 가능 하위 작업) | branch × attempt 격자 | 커널 결정적 검증기 | π_E 의 직접 학습 데이터 |
| 운영 L0(옵트인) | 검증 가능 하위 작업 격자만 | 결정적 검증기 | 구조·점수·비용만 저장, 내용 없음 |

- 세계 메타: 태스크 id, 하네스 버전, 정책(lineage), π_E 버전, 원천, `partial`(조기 종료).
- 세계 간 평균 시 정규화 s̃ (04 문서 E8).
- **세계 풀 분할**: Dream 의 정책 선택에도 과적합이 있을 수 있으므로(같은 세계로 개발·선택) 세계를 *개발용 / 선택용* 으로 나누는 것을 권장한다(논문은 같은 t 세계로 둘 다 함 — 재현 모드에선 논문대로).

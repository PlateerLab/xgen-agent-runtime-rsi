# geny vs geny-rsi — 두 독립 런타임 비교 보고서

> 대상: **geny**(xgen-agent-runtime, XGEN 의 Agent Geny)와 **geny-rsi**(xgen-agent-runtime-rsi, XGEN 의 Agent Geny RSI).
> 모델: gpt-6-sol · claude-sonnet-5(1차, 2026-10-01), gpt-6-luna · claude-haiku-4-5(2차, 2026-10-02).
> 원자료 요약: [data/2026-10-01.json](data/2026-10-01.json), [data/2026-10-02.json](data/2026-10-02.json)(`experiments/summarize.py`, 대화 내용·답 제외).
> 패키지 기준: geny-rsi 0.7.0.
>
> 이 보고서는 두 가지다. (1) 두 런타임이 harness pipeline 만 다르게 제대로 구현됐는지의 검토, (2) RRSI·Dream-RSI 방법론이 동작하는지 잰 실험.
> 실험에서 진화시킨 하네스는 그 실험 스위트·모델에 맞춘 것이라 운영에 쓰지 않는다. 운영의 Agent Geny RSI 는 H0 에서 시작해 XGEN 안에서
> 에이전트마다 그 사용으로 진화한다([설계 40](../design/40-agent-self-evolution.md)).

## 요약

- **두 런타임은 서로 독립이고, 다른 것은 harness pipeline 하나다.** geny-rsi 는 xgen-agent-runtime 을 import 하지도 의존하지도
  않는다. Geny 의 요소 계층(공급자·도구·기억·작업·앱·스토리지·자기 진화·호스트 계약)은 runtime 4.81.0 을 `xgen_rsi.base` 로 복사해
  쓴다(519개 중 517개 파일이 바이트 동일). 한 턴을 실행하는 pipeline 만 다르다 — geny 는 21-stage 엔진, geny-rsi 는 고정 커널 +
  RRSI 가 진화시키는 하네스다(§1).
- **갈아끼워도 잃지 않는다.** 같은 모델 응답을 재생하면 진화 전 geny-rsi(H0)는 geny 와 같은 요청을 바이트 단위로 보낸다(158/158).
  세 스위트·네 모델에서 점수 차이는 전부 잡음 안이다(§3).
- **RRSI 는 진화에 쓴 과제에서 점수와 비용을 고쳤다. 보류 분할에서는 아직 개선이 확인되지 않았다.** luna evolve 0.919 → 0.948(잡음 바닥 위),
  haiku 같은 점수대에서 토큰 −10.6%, sol 0.992 → 1.000. 판정에 쓰지 않은 보류 분할에서는 luna 0.911 vs H0 0.907, sol 1.000 vs 0.997 로
  잡음 안이고 토큰은 각각 +26%, +5% 다(§4, §5).
- **Dream-RSI 는 같은 최고점을 더 적은 탐색으로 찾는 정책을 골랐다.** gpt-6-sol: 시도 −25%, 정책 토큰 −16% 로 승격. gpt-6-luna: 시도 −36%
  후보가 나왔지만 토큰이 +0.16% 라 확인 판정이 막았다(§6).
- **운영에는 H0 만 싣는다.** 실험 하네스는 합성 스위트에 맞춘 것이다. 0.5.0 에서 모델별로 실었던 실험 하네스 3종을 0.6.0 에서 뺐다. 모든
  Agent Geny RSI 는 RSI 파이프라인의 기본값(H0)에서 시작하고, 그 에이전트의 사용(턴 기록·피드백·기대 답)을 과제로 삼아 자기 하네스를
  진화시킨다(§7).
- **평가 환경은 Geny 의 요소 일부를 끈 상태였다.** 오프라인 평가는 기억·작업·자기 진화·코드 실행 없이 파일 도구 5종으로만 돌았다. 그래서
  이번 숫자는 "하네스가 파일 업무를 어떻게 처리하는가" 이고, 하네스와 기억·코드 실행의 상호작용은 측정되지 않았다(§10).

## 1. 두 런타임 — 무엇이 같고 무엇이 다른가

### 1.1 구성

| | **geny** — Agent Geny | **geny-rsi** — Agent Geny RSI |
|---|---|---|
| 패키지 | xgen-agent-runtime | xgen-agent-runtime-rsi. 서로 import·의존하지 않는다 |
| 진입점 | `AgentTurnExecutor().run(host, **kwargs)` | `GenyRSITurnExecutor().run(host, **kwargs)` — 같은 계약 |
| Geny 요소 계층 | runtime 자체 | runtime 4.81.0 사본 `xgen_rsi.base`(파일 해시를 `COPY.json` 에 기록, 테스트로 검사) |
| 턴 조립(호스트 계약) | `AgentTurnExecutor.run` 안 | `xgen_rsi.assembly` — 같은 조립을 떼어 둔 사본 |
| **harness pipeline** | 21-stage 엔진. 사람이 측정하고 릴리스로 고친다 | 고정 커널 K₀ + 하네스 H(𝒦 9종 구성요소). 모델 계열별 RRSI 채택 하네스를 쓴다 |
| 하네스 개선 | 사람 | **RRSI**(오프라인 라운드: 제안 → 누설 심사 → 평가 → 잡음 바닥·비용 규칙으로 채택) |
| 탐색 정책 | 없음 | **Dream-RSI** 가 진화시키는 π_E(검증기가 있는 라이브 탐색에서 쓴다, §6) |

```
에이전트 A = (π, K₀, H, π_E)
  π    고정 정책   사용자가 고른 공급자·모델                                   두 런타임 같음
  K₀   고정 커널   I/O 계약 · 공급자 관문 · 사용량 원장 · 도구 권한 · 한도 · 기록     하네스로 못 바꿈
  H    하네스     𝒦 9종 타입 구성요소의 내용 주소 패키지                         RRSI 가 진화
  π_E  탐색 정책   분기·배치·정지를 정하는 코드                                   Dream-RSI 가 진화
```

geny-rsi 의 운영 턴은 그 에이전트의 하네스로 돈다. 모든 에이전트는 H0 에서 시작한다 — H0 는 geny 의 동작을 구성요소로 옮긴 시작 하네스이고,
§3 의 재생 동등성으로 같은 요청을 보낸다는 것을 실측했다. 그 뒤 하네스는 그 에이전트의 사용으로 RRSI 가 진화시킨다(§7). π_E 는 운영 대화
턴에서는 쓰이지 않는다 — 대화 턴에는 결과를 채점할 검증기가 없어서 한 경로로 돈다(§6).

### 1.2 구현 검토 (0.6.0)

두 런타임의 턴 경로를 코드와 대조 실행으로 검토했다(같은 입력을 두 엔진에 넣고 요청·청크·기억 기록을 비교, 모델 호출 없음).

**독립성.** geny-rsi 소스에 xgen-agent-runtime import 가 없고(`tests/test_independence.py`, CI 는 runtime 이 없는 환경에서 돈다), 사본은
기록과 같다(`tools/sync_base.py --check`: 519 파일, 기록된 수정 3건). 사본의 턴 실행·조립 관련 파일(turn_executor·runner·pipeline·stage)은
모듈 경로만 바꾼 원본(4.80.0, 0.6.0 에서 4.81.0 으로 갱신 — 4.81.0 은 웹 검색 도구 두 파일만 바뀌었다)과 바이트 동일하다. `xgen_rsi.assembly` 는 원본 4.79.0 의 `assemble_turn` 과 import 순서만 다르고, 4.80.0 의
`AgentTurnExecutor.run` 조립과는 동작이 같다(차이 다섯 곳은 기록 방식·오류 반환 방식·자원 정리 자리로, 출력에는 영향이 없다).

**Geny 요소 — H0 에서 같은 것.** 빠진 요소는 없다.

| 요소 | 두 엔진의 같은 점(H0) |
|---|---|
| CLI 백엔드(claude_code·codex) | CLI 를 1회 호출하고 루프는 CLI 가 가진다. MCP 브릿지 도구 표면·네이티브 도구 차단이 같은 조립 코드. 청크·시스템·메시지·기억·증류 실측 동일 |
| 작업 | Job 도구, 예약 실행 턴의 JobSchedule 제외, 작업 프롬프트 — 같은 조립 코드 |
| 압축 | 비용 기준 정리, 창 80% → 70% 요약, 예산 가드. 압축 호출을 포함한 요청 실측 동일 |
| 기억 | 검색 주입(같은 retriever), 시스템 프롬프트의 기억 블록, 슬라이스 끝 STM·rollup, 증류·끝나지 못한 턴 기록(같은 함수), 읽기 전용 블록 |
| 자기 진화 | 자기 진화 블록과 WorkflowSelf — 같은 조립 코드 |
| 도구·앱·스토리지 | 내장·저장·앱 도구, 작업 공간 복원, 노출(core/deferred·ToolSearch·문·이력 복원), 결과 필터·권한·거부·반복 차단 — 턴 중 ToolSearch 활성화까지 요청 실측 동일 |
| 루프·출력 | repeat-stop·산출물 대조·턴 입력 예산, 구조화 출력, max_iterations·이어가기, thinking, 이미지·첨부·로컬 폴더, 취소, 청크 형식·usage·`[ERROR]` 청크, 프롬프트 캐시 |
| 위임(`enable_delegation`) | 두 엔진 모두 없다(runtime 4.71.0 에서 제거). CLI 의 Task/Agent 는 차단 |

**하네스 때문에 다른 것.** 0.6.0 패키지는 H0 만 실으므로 진화 전에는 없다. 에이전트가 진화하면 그 에이전트의 채택 하네스만큼 다르다.
(0.5.0 은 계열 표가 gpt-6-luna·gpt-6-sol·claude-haiku-4-5 를 실험 하네스로 보냈고, 그중 `sol-xgen-hard` 는 `memory.archive=false` 라 gpt-6-sol
턴의 STM 기록이 0건이었다 — 대조 실행으로 확인한 뒤 0.6.0 에서 실험 하네스를 모두 뺐다.)

**H0 에서도 다른 것.**

| 항목 | geny | geny-rsi | 영향 |
|---|---|---|---|
| 하네스를 못 읽을 때(`XGEN_RSI_HARNESS_DIR`·`XGEN_RSI_LINEAGE_FILE` 경로 오류) | 해당 없음 | `[ERROR] geny agent could not start` 로 턴을 시작하지 않는다. H0 로 돌아가지 않는다 | 관리자 설정 오류가 바로 드러난다. 0.6.0 에서 이 경우에도 조립이 만든 자원(CLI 작업 공간·브릿지 토큰·샌드박스 반영)을 정리하도록 고쳤다 |
| rollout 기록(관리자 옵트인) | 기록 실패 시 턴이 `[ERROR]` 로 끝남, stage 이벤트 포함 | 기록 실패는 로그만 남기고 턴은 계속, stage 이벤트 없음 | 감사 기록의 모양과 실패 처리가 다르다 |
| 첨부가 있는 턴의 실행 기록 카드 | 기록되지 않음(runtime 쪽 결함: dict 입력에서 조용히 실패) | 글로 바꿔 기록 | geny-rsi 쪽이 맞다 |
| 도구 레지스트리가 빈 SDK 턴에서 모델이 도구를 부를 때 | 한 번 더 호출 | 바로 완료 | 운영에서는 내장 도구·ToolSearch 가 늘 있어 영향이 낮다 |
| 관측 필드 | 호출 목적 `api`, stage 이벤트, `cache_key` | 호출 목적 `main`, 궤적 기록(`XGEN_RSI_RECORD_DIR` 일 때) | 사용자 출력 무관. `XGEN_RSI_RECORD_CONTENT` 를 켜면 전사가 디스크에 남는다 |

**운영 턴에서 π_E 는 돌지 않는다.** 운영 경로(`turn_executor`·`assembly`·`kernel`·`components`·`harness`)는 explore·dream·discovery·evolve 를
import 하지 않고, 실제로 턴을 돌린 뒤에도 그 모듈은 로드되지 않았다. `exploration_policy` 는 궤적 기록의 라벨과 하네스 버전 해시에만 쓰인다.

**XGEN 쪽.** XGEN workflow 에서 에이전트에 딸린 기능이 그 에이전트의 패키지로 도는지 검토했다. 대화 턴·기억·제작 도구·작업·앱·스토리지·고정·복제·예약
작업은 Agent Geny RSI 를 `xgen_rsi.base` 로 다뤘다. 틈은 패키지 문맥이 끊기는 자리(다른 스레드, 본문에만 워크플로우가 있는 요청)에서 기본값
runtime 으로 돌아가는 것이었고, 아래를 고쳤다(workflow !2056, 회귀 테스트 6개 — 마스킹·캐시 테스트는 수정 전 코드에서 실패 확인).

| 틈 | 영향 | 고친 것 |
|---|---|---|
| CLI 백엔드(claude_code·codex) 턴의 도구 결과에 통제 정책 마스킹이 안 걸림 | RSI 에이전트의 웹·MCP 결과가 가려지지 않고 모델에 갔다(Agent Geny 는 가려짐) | 출처 판정을 도구 자신의 패키지로(`masks_result_of`) |
| 웹 검색 도구 차이 | Agent Geny 만 runtime 4.81.0 의 막힘 구분·재시도를 썼다 | rsi 사본을 4.81.0 으로 갱신 |
| 앱 LLM 클라이언트 캐시 키에 패키지가 없음 | 두 종류 에이전트의 앱이 서로의 클라이언트를 받았다 | 키에 패키지 포함 |
| 구형(스타 아닌) 그래프에서 RSI 에이전트에 붙인 ComfyUI 도구가 빠짐 | 도구가 조용히 사라졌다 | 구형 실행기도 그래프 에이전트의 패키지로 노드를 돈다 |
| 공용 도구 [테스트]·승격·갱신, IDE 세션 준비, 대화 모델·생각 선택이 runtime 으로 | 검증이 "그 에이전트가 부를 때와 같은 경로"가 아니었다 | 세션 준비·승격을 워크플로우 기준으로, 본문 워크플로우 엔드포인트는 그 패키지로 들어간다 |
| 캔버스 AI 빌더가 `agents/geny` 만 앎 | 기존 RSI 에이전트의 프롬프트·모델 갱신 누락, 그림자 QA·자동 복구 거부, 시작 노드 합성 | 두 종류를 같은 에이전트로 본다(새로 만들 때 기본값은 Agent Geny 그대로) |

남은 차이(기능 영향 없음): 증류 백그라운드 스레드와 통제 정책의 내장 도구 이름표가 runtime 쪽 문구·이름을 읽는다 — 사본이라 내용이 같다.

## 2. 평가 방법

**호스트.** `EvalHost`(`xgen_rsi.host.LocalHost` 기반). 시행마다 독립 작업 공간을 만들고, 파일 도구 5종(Read·Write·Edit·Glob·Grep)만 그
안으로 준다. 기억·작업·커넥터·자기 진화는 없고 코드 실행 도구도 없다. 시작 파일의 수정 시각은 경로 순으로 고정한다(Glob 결과 순서가 실행마다
같도록, §3).

**엔진.** 1차는 두 엔진 모두 xgen-agent-runtime 4.78.0 wheel 위에서 돌렸다(당시 geny-rsi 0.1~0.2 는 runtime 을 라이브러리로 썼다). 2차의 geny 는
rsi 안의 사본(`xgen_rsi.base`, runtime 4.80.0 과 517/519 파일 바이트 동일)으로 돌렸다.

**스위트.** 셋 다 이 저장소에 있고 8범주 × 4과제(evolve 24 · heldout 8 · smoke 2)다. 정답은 전부 코드로 계산하고, 과제마다 오라클 만점·빈 답
0.5 이하를 테스트로 고정한다.

| 스위트 | 노리는 지점 |
|---|---|
| `xgen-core` | 과제마다 규칙 하나인 업무(CSV 집계·필드 추출·주간 보고·설정 수정·형식 계약·계산·회의록·파일 이름 복구) |
| `xgen-hard` | 양(주문 90행+ 등)·규칙 문서(정정·반품·부가세)·함정(시행일 뒤 부칙, 연기된 일정, 폐기본)·두 단계 정합성 |
| `xgen-pro` | 회의록 20건(7만 자+) 추적, 장부·환율 대조, 연락처 100행+ 변환, 설정 24개 이관, 정책 개정 12건 우선순위, 일정 퍼즐, 문서 56개+ 검색, 감사 정정 |

xgen-pro 는 천장 아래 모델을 위해 만들었다. heldout 1회 파일럿으로 세 번 키웠다(luna 0.896 → 0.934 → 0.932·0.908).

**모델.** 정책: gpt-6-sol, claude-sonnet-5, gpt-6-luna, claude-haiku-4-5. RRSI 역할 모델(제안·검토·분석·요약): sol·sonnet 진화는 자기 자신,
luna 진화는 gpt-6-sol, haiku 진화는 claude-sonnet-5.

**지표.** S = 검사 가중 평균 보상(RRSI Eq.3, 누락은 0 으로 분모에 포함). ± = 과제 평균의 표준오차. 토큰 = 시행당 외부 usage(입력+출력, 두 엔진이
같은 정의로 낸다). RRSI 의 Ĉ 와 Dream 확인의 비용은 geny-rsi 원장의 정책 토큰이다. 잡음 바닥 δ 는 기준 하네스를 두 번 평가해 보정했다(z=2).

## 3. 교체 동등성 — 진화 전 geny-rsi(H0) vs geny

### 3.1 결정적 재생

## 6. Dream-RSI 탐색 정책

**무엇을 하나.** 검증기가 있는 과제를 branch × attempt 격자로 실제로 풀어 보는 라이브 탐색(`rsi dream explore`)에서, π_E 가 몇 갈래로 나누고
언제 멈출지 정한다. 쌓인 탐색 트리가 재생 world 가 되고, 후보 정책을 새 생성 없이 재생해 Eq.1 `V = max s − β1·N + β2·N/max(1,k★)` 로 비교한다.
재생 승자는 같은 과제를 실제로 다시 탐색해 RRSI 판정(바닥 + 비용 규칙)을 통과해야 승격한다. 시작 정책은 π₁(`parallel_refine`, 논문의 초기 정책).

| 정책 모델·스위트 | world | 개발자 | 재생 선택 | 라이브 확인(8과제, 같은 격자) | 결과 |
|---|---|---|---|---|---|
| gpt-6-sol · xgen-hard | 트리 40 | gpt-6-sol | `r0002_dev` | 최고점 1.0 = 1.0, **시도 72 → 54(−25%)**, 정책 토큰 433,669 → 363,750(**−16.1%**) | **승격** |
| gpt-6-luna · xgen-pro | 트리 16 + 시행 24 | gpt-6-luna(논문 설정) | 후보 V 가 현재 정책과 같음(1.0253) | — | 현재 정책 유지 |
| gpt-6-luna · xgen-pro | 같음 | gpt-6-sol | `r0002`(V 1.0284 > 1.0253) | 최고점 1.0 = 1.0, **시도 72 → 46(−36%)**, 정책 토큰 1,767,375 → 1,770,254(+0.16%) | **거절**(비용 규칙) |

- luna 가 만든 두 정책은 만점을 찾은 뒤에도 탐색을 멈추지 않아 π₁ 과 같은 행동을 했다.
- gpt-6-sol 이 luna 용으로 만든 정책은 시도를 36% 줄였지만 시도 하나가 길어져 토큰이 줄지 않았다. 재생은 시도 수를, 확인 판정은 토큰을 보므로 둘이
  갈렸고 확인 단계가 승격을 막았다.
- claude-sonnet-5 사이클은 사이클 1 도중 중단, haiku 는 돌리지 않았다(크레딧).
- **운영과의 관계.** 운영 대화 턴은 검증기가 없어 탐색 없이 한 경로로 돈다. 운영에서 Dream-RSI 의 world 는 각 에이전트의 진화 실행이 남긴
  평가 시행이다(설계 40 §2.5). 실험에서 승격된 sol 정책은 그 실험의 world 에 맞춘 것이라 패키지에 넣지 않았다.

## 7. 운영 적용 — H0 에서 시작해 에이전트마다 진화

**패키지에는 H0 만 싣는다.** 실험에서 진화시킨 하네스(§4)는 합성 스위트(xgen-hard·xgen-pro)와 특정 모델에 맞춘 것이다. RSI 의 강점은 사용자
fit 이므로 이런 하네스를 미리 넣으면 각 에이전트가 자기 사용에 맞춰 나아갈 출발점을 실험 스위트 쪽으로 틀어 버린다. 그래서 운영의 출발점은
모든 에이전트가 같은 H0 다.

**경위.** 0.5.0 은 실험 채택 하네스 3종(`luna-xgen-pro`·`sol-xgen-hard`·`haiku-xgen-pro`)을 모델 계열 표로 실었고, XGEN develop 이 그 버전을
고정했다(workflow !2054). 0.6.0 에서 그 하네스와 계열 항목을 모두 지우고 표를 `{"default": "h0"}` 로 되돌렸다. 테스트가 패키지에 H0 하나만
있는지, 어떤 모델이든 H0 로 시작하는지 확인한다.

**운영 구조**([설계 40](../design/40-agent-self-evolution.md)).

| 단계 | 무엇 | 재료·근거 |
|---|---|---|
| 턴 | 그 에이전트의 현재 하네스로 돈다(처음에는 H0). 궤적 요약(하네스 버전·종료·도구·비용)을 에이전트별로 남긴다 | 호스트 훅 `rsi_agent_harness`·`rsi_record` |
| 과제 | 그 에이전트의 사용을 판정 기준이 붙은 과제로 만든다 | `execution_io`(턴 입력·출력), `user_feedbacks`(별점·이슈·코멘트), 기대 답(품질평가), 사용자가 넣은 과제 |
| 진화 | 그 과제로 RRSI 라운드를 돈다(평가는 독립 작업 공간, 부작용 있는 도구는 막음) | 정책 = 그 에이전트의 모델, 역할 모델 = XGEN 등록 LLM |
| 채택 | δ·비용 규칙·가드를 통과한 편집이 그 에이전트의 다음 하네스가 된다. 판정 근거가 남고 되돌릴 수 있다 | 에이전트별 하네스 계보 |

구현 상태: 1단계(패키지를 H0 만으로·두 런타임 동일성 결함 수정, rsi 0.6.0·workflow !2056)와 2단계(rsi 의 에이전트 하네스·궤적 훅, 기준 판정
검사·판정 모델, 사용 기록 → 과제, 에이전트 진화 API — 0.7.0)는 끝났다. 2단계는 사용 기록 → 과제 → RRSI 라운드 → 채택 → 다음 턴이 채택 하네스로
도는 것까지 각본 모델로 끝까지 테스트한다. 3단계(XGEN 저장·진화 작업자·API)와 4단계([하네스] 탭)는 진행 중이다.

## 9. 결론 — geny-rsi 가 더 강하게 달성한 것과 아직 못 한 것

| | 실측으로 보인 것 | 아직 보이지 못한 것 |
|---|---|---|
| 교체 | 같은 응답 → 같은 요청(158/158). 세 스위트·네 모델에서 진화 전 점수 차이 잡음 안 | — |

geny 와 비교해 geny-rsi 가 더 강하게 하는 것은 **하네스 변경을 측정으로 고르고 그 근거를 남기는 것**이다. 사람이 손으로 하던 하네스 판정
(점수 비열등 + 비용 감소면 채택)을 잡음 바닥·비용 규칙으로 기계화했고, 손해 보는 변경을 자동으로 거른다. 합성 스위트의 보류 분할에서 점수가
오른다는 것은 아직 보이지 못했다. 운영에서는 이 판정이 각 에이전트의 실제 사용을 재료로 돈다 — 실험 스위트가 아니라 그 에이전트가 실제로 받는
일과 사용자의 평가가 기준이 된다.

## 10. 한계와 남은 일

- **평가에서 꺼 둔 Geny 요소.** 오프라인 평가는 기억·작업·커넥터·자기 진화·코드 실행 없이 파일 도구 5종으로 돌았다. 하네스가 기억을 어떻게
  주입·기록하는지, 코드 실행이 있을 때 절차가 어떻게 달라지는지는 측정되지 않았다. sol 실험 하네스의 `memory.archive=false` 가 그 결과다.
  `EvalHost` 에는 `workspace+bash` 도구 묶음이 있지만 이번 실험에는 쓰지 않았다.
- **표본.** 보류 분할은 범주당 과제 하나(8과제)라 0.02~0.03 차이를 가리기 어렵다(± 0.07).
- **띠 안 채택.** 새 구조 가점을 포함한 띠 안 규칙은 잡음 안의 이득도 채택한다. 이번 채택 대부분이 이 규칙으로 들어왔다.
- **미완 계보.** haiku 진화 2/5 라운드(보류 분할·Dream 미실행), sonnet-5 진화·Dream 중단.
- **운영 턴의 탐색.** π_E 는 검증기가 있는 탐색에서만 쓰인다. 운영 대화 턴은 한 경로로 돈다.
- **에이전트별 자가 진화.** XGEN 안에서 에이전트마다 사용 기록을 과제로 만들어 하네스를 진화시키는 구조(§7)는 구현 중이다.
- **운영 요소를 켠 XGEN 턴 확인.** 기억·내장 도구·위임·자기 진화를 켠 Agent Geny RSI 턴은 XGEN 서버에서 확인해야 한다(로컬에는 DB·샌드박스가 없다).

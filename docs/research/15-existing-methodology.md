# 15. 우리의 기존 방법론 — 증거 기반 하네스 엔지니어링 (CHANGELOG 4.27–4.75 실록)

> 출처: `xgen-agent-runtime/CHANGELOG.md` (4.27.0, 2026-09-17 ~ 4.75.0, 2026-10-01). 각 항목은 해당 버전 절의 문장을 근거로 한다. 코드가 아니라 **개발 기록**이므로 실험의 원자료(로컬 실험실 `harness-bench/lab` 의 실행기·채점기)는 이 머신에서 찾지 못했다(위치 미확인 — PLAN 결정 D-8).

## 1. 실제로 해 온 일 — 일곱 가지 관행

### 1.1 실측으로 원인을 먼저 해부한다 ("근거:" 로 시작하는 절)

| 버전 | 해부 대상 | 발견 |
|---|---|---|
| 4.27.0 | dev 위배상품 점검 3회(claude-sonnet-4-6) | 입력 24.9만, 왕복 약 19, 같은 검색 품목별 13회, 인자 타입 오류 재시도 6–15회 → **비용 = 고정 앞부분 × 왕복 수** 를 목표식으로 둠 |
| 4.29.0 | dev 실사용 도구 12회+ 턴 73건 사람 라벨링 | 낭비 루프 14 / 정상 55 |
| 4.30.0 | Harness-Bench(Qihoo360) 68과제 기준선(Qwen3.8-27B) | 완료율 0.826, 잃은 점수 = 내용 정확성 75% / 근거·금지 13% / 형식·계약 10% / 도구·복구 0% |
| 4.31.0 | dev 28일 7,159턴·입력 2.36억 | 100만 초과 11턴(0.15%)이 입력 24%, 300만 초과 3턴이 19% |
| 4.32.0 | 고정 프리픽스(Qwen 토크나이저) | 호출당 고정분 ≈ 8,600토큰 중 도구 스키마 72%, 자기확장 도구 6종이 모든 호출에 실리는데 사용 턴은 0–2.4% |
| 4.61.0 | 호출 해부(설계 38과제) | 과제당 호출 10.8 중 입력 읽기 4.2회(39%) |

→ RRSI 의 **ANALYZE(analyst + digester, 3-렌즈 보고서)** 를 사람이 하던 것이다. 손실 원인 가중 분해는 analyst 의 "총 영향 순위" 와 같다.

### 1.2 설계 집합과 홀드아웃을 나눠 판정한다

| 버전 | 설계 | 홀드아웃 | 비고 |
|---|---|---|---|
| 4.29.0 | 라벨 14건(낭비) + 정상 55 | 7/28–9/4 기간 41건 | "설계에 쓰지 않은 기간으로 검증" |
| 4.61.0 | 38과제 | 29과제 | Harness-Bench, 로컬 실험실 |
| 4.63.0 | 39과제 | 31과제 | 70과제 × 2회 |

→ RRSI 의 **D_evolve / ID held-out** 분리와 같다. 다만 판정 규칙이 수식이 아니라 사람의 판단이었다.

### 1.3 반복 측정으로 잡음을 본다

- 4.63.0: 같은 설정 2회의 점수 0.847 · 0.807 — "1회차 상승분은 흔들림", "같은 설정 2회 차이 0.06 범위"(4.63.2).
- 4.45.0: 카나리 ×2 vs dev ×3 왕복 비교(28·20 vs 28·21·17).
- 4.30.0: "024·033·052 의 상승은 실행 간 편차".

→ RRSI 의 **잡음 대역 δ** 를 사람이 눈으로 추정하던 것이다. 70과제 × k=2 에서 0.04–0.06 흔들림이면, RRSI 식으로 재면 δ ≈ 2·sd(null ΔS) 가 그 정도 규모라는 뜻이다(실측 보정 필요, 34 문서).

### 1.4 점수는 비열등, 비용은 줄어야 채택한다

- 4.63.0: 왕복 8.21 → 4.54/4.67, 입력 77k → 42k/43k, 점수 0.807 → 0.847/0.807 — "점수는 비열등" 으로 채택.
- 4.63.2: 왕복 4.54·4.67 → 3.91, 입력 42k·43k → 34k, 점수 0.847·0.807 → 0.805 — 비열등 판단(떨어진 과제 원인 분석 동반).
- 4.30.0: "항상 보여 주는 판"은 점수 0.757 → 0.813 이지만 왕복 +23%·입력 +23% → **"문제가 있을 때만" 판 채택**(유휴 비용 0).

→ RRSI 의 **대역 안 규칙(Eq.17, 비용 절감이 양의 기여)** 과 **비용 규칙(Eq.7, 비용 증가는 이득으로만 정당화)** 의 정성판이다. 4.30.0 의 판단은 정확히 "ΔS 의 일부는 잡음, ΔC +23% 는 실제" → 기각, 이었다.

### 1.5 프롬프트 부탁보다 구조를 바꾼다

- 4.61.0: "프롬프트의 '한 번에 묶어라' 는 따르지 않았다(ToolBatch 38과제 중 1회)" → 참조 파일 자동 첨부(구조).
- 4.62.0: "시스템 프롬프트의 'sandbox 에 없다고 없는 게 아니다' 는 이미 들어가 있었다 — 부탁은 통하지 않았다" → 도구 결과 끝 한 줄(구조).
- 4.63.0: "프롬프트로 '묶어라' 는 통하지 않았다 — 구조로 바꾼다" → 작은 작업 폴더 빠른 경로.

→ RRSI 헌법 hard rule 4 **"Mechanism over wording"** 과 같은 원칙에 독립적으로 도달해 있었다.

### 1.6 설명되지 않는 변화는 싣지 않는다 / 낮은 변형은 기각한다

- 4.45.0 Not shipped: 카탈로그 접기 — 홀드아웃 040 이 왕복 47–70 으로 늘어 "텍스트의 어느 부분이 행동을 바꾸는지 설명되기 전에는 싣지 않는다".
- 4.63.0: "일반 경로에 계약 사용 안내를 넣는 변형은 점수가 낮아 기각".
- 4.30.0: "답변에 언급만 된 경로가 없는 것은 신호로 쓰지 않는다 — 오탐으로 왕복 +4–7".

→ RRSI 의 **바닥(Eq.5)** 과 **증거 인지 신용 할당**(거부된 메커니즘은 부정 증거로 기록)의 정성판. 다만 기각 기록이 CHANGELOG 문장으로만 남아 다음 제안의 *조건*으로 기계적으로 쓰이지 않았다.

### 1.7 결정론 신호가 있을 때만 끼어든다 (유휴 비용 0)

- 4.30.0 완료 직전 산출물 대조: 깨진 JSON·ragged CSV·빈 데이터 파일·사라진 파일일 때만 발동, 문제 없으면 무음.
- 4.29.0 같은 호출·같은 결과 반복: 결과가 같을 때만 센다.
- 4.62.0 second machine: 사용자 PC 문이 있을 때만, 턴당 2번까지.

→ RRSI critic 규칙 6(무한 작업 금지, 제한된 패스)과 헌법 hard rule 8(종료를 위태롭게 하지 마라) + 비용 규칙을 동시에 만족하는 설계 습관이다. RRSI 의 `trigger_condition` 필드("'always' 는 거의 맞지 않다")와 정확히 같은 생각이다.

## 2. 기존 방법론 ↔ RRSI ↔ Dream-RSI 대응

| 기존 관행 | RRSI 대응 | 부족했던 것 | 새 프레임워크에서 |
|---|---|---|---|
| 원인 해부(실측·라벨링) | ANALYZE: analyst + digester 3-렌즈 | 사람 시간에 묶임(RRSI 서론: "엔지니어가 읽을 수 있는 trajectory 수가 진척을 제한") | digester 병렬 + 사람은 보고서 검토 |
| 설계/홀드아웃 분리 | D_evolve / ID held-out / OOD | OOD 없음, 분리 기준이 회차마다 다름 | 고정 분할 + OOD 세트(34 문서) |
| 2–4회 반복 측정 | δ = z·sd(null ΔS), k 시행 | 눈대중, 바닥 규칙 없음 | 보정된 δ, Eq.5 바닥 |
| "점수 비열등 + 비용 감소면 채택" | Eq.17 (대역 안), Eq.7 (이득 시 비용 규칙) | 정량 기준 없음, 회차마다 판단 | 수식 판정 + 재판정 가능 기록 |
| 구조 > 부탁 | 헌법 hard rule 4 | 헌법 문서 없음 | XGEN 헌법(SKILL.md) 명문화 |
| 설명 안 되면 보류 / 낮으면 기각 | 바닥 + 𝓛_t 부정 증거 | 기각 기록이 CHANGELOG 문장 | 편집 이력 JSONL, proposer 조건 |
| 결정론 신호 시에만 개입 | trigger_condition, critic 6, 비용 규칙 | 관행 | 헌법 + critic 규칙 |
| `harness_components` 발화 카운트 | 구성요소 태그 + 가지치기 g_t | 발화 수만 있고 이득 귀속 없음 | g_t(ℓ) 와 𝓑_t 로 "자리를 버는가" 판정 |
| 카나리 (실서비스 일부) | (없음 — RRSI 는 오프라인) | — | 승격 파이프라인 canary 단계(31 문서 §6.3) |
| Codex 세션이 설계·구현(4.63.0) | proposer 에이전트 | 일회성 | proposer 를 엔진으로 |
| (없음) | — | 탐색 비용 큼(70과제 × 2회 × 변형 수) | Dream-RSI 재생, 정확 경계 조기 종료(33 문서 §4) |

## 3. 기존 방법론이 RRSI·Dream-RSI 에 *더해 주는* 것

1. **실서비스 신호**: dev `agent_trace_spans`, 28일 사용 분포(p50/p95/p99), 사용자 라벨. RRSI 는 벤치마크만 본다. 우리는 운영 분포를 OOD·가드 설계에 쓸 수 있다(예: "실사용 턴 분포에서 입력 p99 를 넘기지 않는다" 를 도메인 가드로).
2. **다중 모델 현실**: 같은 수정이 gpt-4.1·qwen 계열에서만 필요했던 사례(4.29.0 "반복은 전부 gpt-4.1·qwen 계열에서") → lineage 별 하네스(30 문서 P8)의 직접 근거.
3. **고정 프리픽스 비용 모델**: "비용 = 고정 앞부분 × 왕복 수"(4.27.0) — RRSI 의 ΔC 를 분해해 proposer 에게 보여 줄 진단(고정분·왕복·도구 결과 크기)으로 쓴다.
4. **안전 우선 문화**: 거부 우회 삭제(4.61.0), PC 에서 `rm -rf`(4.62.0) 같은 사고를 하네스 장치로 막아 온 기록 → critic 규칙에 "사용자 거부·권한 우회" 를 XGEN 전용 거부 사유로 추가(35 문서).
5. **카나리 문화**: 오프라인 판정 뒤 실서비스 일부 적용 → 승격 파이프라인의 마지막 단계.

- RRSI 의 workspace 인스턴스(Harvey LAB: evolve 120 / held-out 40, criteria judge)와 구조가 닮았다. **D_evolve = 설계 세트, ID held-out = 홀드아웃 세트** 로 바로 쓸 수 있고, 기존 런타임 4.75.0 기준선이 곧 H_0 측정이다.
- 문제: 설계 세트 ≈ 39과제는 RRSI 인스턴스(89–120)보다 작다 → δ 가 커지고(같은 k 에서 sd ↑) 미세 개선을 못 잡는다. k 를 늘리거나(비용↑) 과제를 보강해야 한다(34 문서에서 비용 추정).
- 실험실 코드 위치 확인이 Phase 5 의 선행 조건이다(결정 D-8).

# 20. 세 방법론 비교 종합 — 기존 런타임 · RRSI · Dream-RSI

> 01–05(논문·코드), 10–14(기존 런타임 조사)를 바탕으로, 세 방법론이 **무엇을 최적화하고 무엇을 고정하며 어디서 충돌·보완하는지**를 정리한다. 융합 설계 원칙은 [../design/30-fusion-philosophy.md](../design/30-fusion-philosophy.md) 에서 이 문서를 근거로 확정한다.

## 1. 층위가 다르다 — 무엇을 바꾸는가

| | 기존 xgen-agent-runtime | RRSI | Dream-RSI |
|---|---|---|---|
| 최적화 대상 | (최적화 루프 없음) 사람이 설계한 21-stage 파이프라인 + manifest + 프롬프트. 세션 범위 자기 수정(`env` 도구) | **하네스 H** (객체 수준: 에이전트가 태스크를 *어떻게 수행하는가*) | **탐색 정책 π_E** (메타 수준: 발견 계산을 *어디에 얼마나 쓰는가*) |
| 고정되는 것 | — | 정책 π, 도구 환경, 채점기, 태스크 집합, 인터페이스 계약, 모델명·스텝 예산·타임아웃 | discovery agent, 모델, 평가기, 실행 인터페이스 |
| 변경 단위 | stage/strategy 교체, manifest 편집, `env` 도구 편집 | 구성요소 태그(𝒦) 붙은 원자 편집, b_t 개 이하 묶음 | 정책 코드 버전(π^0..π^{M−1}) |
| 평가 방식 | 테스트 스위트(결정적 fake LLM 위주) | evolve 집합 k 시행 **실제 실행** (비쌈) | 기록된 발견 트리 **재생** (거의 공짜) |
| 수락 규칙 | 사람 리뷰·머지 | 비보상적 논리곱: 누설 심사 ∧ 바닥 ∧ 비용/대역 규칙 ∧ 가드 | 현재 정책 포함 argmax V^m (재생 위 비퇴화) |
| 이력의 역할 | 로그·감사 | 증거(𝓛_t): 반증된 가설 재사용 방지, 가지치기, 탐색 방향 | 세계(𝓗_t): 대안 정책을 실행해 보는 시뮬레이터 |
| 과적합 방지 | 없음(최적화 안 함) | 핵심 목적 — 7가지 정규화 | 명시적 장치 없음(재생은 관측된 공간만 봄; prefix-only 규칙과 "trace 특화 값 복사 금지"로 누설 차단) |
| 비용 관점 | 달러 비용 추적(결함 있음, 12 문서) | 정책 토큰, **상대** 변화, Ridge 식 규칙 | probe 수(생성–평가 요청 수), 병렬성 |

**결론 1**: RRSI 와 Dream-RSI 는 경쟁 관계가 아니다. **RRSI 는 "무엇을 바꾸고 무엇을 남길지", Dream-RSI 는 "탐색 계산을 어떻게 쓸지"** 를 다룬다. 기존 런타임은 둘 다 갖고 있지 않지만, 그 둘이 작동할 **실행 기반(다중 공급자, 도구, 샌드박스, 이벤트, 지속성)** 을 이미 갖고 있다.

## 2. 같은 구조, 다른 이름 — 개념 대응표

| 개념 | 기존 런타임 | RRSI | Dream-RSI |
|---|---|---|---|
| 고정 모델 | `ModelConfig` (대화별 선택, 다중 공급자) | π (frozen policy) | discovery agent 의 LLM |
| 행동을 정하는 코드 | 21 stage + strategy slot + host 코드 | H (harness) | π_E (exploration policy) + 오케스트레이션 계층 |
| 행동을 정하는 텍스트 | preset 프롬프트, 도구 설명, 완료 마커 지시 | `prompt` 구성요소 | 탐색 프롬프트(B.1) |
| 행동 설정 | manifest, `PipelineConfig`, `ModelOverrides`, env vars | `config` 구성요소 | β, GridPlan(B, R) |
| 구성 산출물 | `EnvironmentManifest` (JSON) | git commit (harness_tree 해시) | 정책 파일 `method.py` 버전 |
| 실행 기록 | `PipelineEvent` 스트림, rollout recorder, execution record | trajectory (render_trace) | 발견 트리 노드(스냅샷·산출물·진단·점수) |
| 품질 신호 | s14 evaluate(자체 판단) | r(x,τ) 외부 검증기 | s_v (evaluator 점수) |
| 비용 신호 | `TokenUsage`, s07 가격 | c(τ) 정책 토큰 | N (probe 수), k★ (라운드) |
| 자기 수정 | `env` 도구 (세션 범위, 평가 없음, 롤백 없음) | proposer + critic + 선택 (전역, 평가, 이력) | policy-development agent + 재생 선택 |
| 안전 게이트 | permission, HITL, guard stage, forged tool 테스트 게이트 | critic 6규칙, smoke, 누락 게이트, 도메인 가드 | prefix-only, 정보 은닉, 지원 밖 처리 |
| 구성요소 분류 | stage 번호(1–21), `harness_components.py` 층 | 𝒦 9종 | (단일 정책 파일) |

## 4. 충돌 지점과 조정

### 4.1 "하네스는 고정 정책 위에서 진화" vs "사용자는 대화마다 모델을 고른다"

- RRSI 는 π 를 고정하고 H 를 진화시킨다(Table 3: 정책별 독립 진화). XGEN 은 대화·노드마다 공급자/모델을 바꿀 수 있다(다중 공급자 유지가 사용자 요구).
- **조정**: 하네스 **계보(lineage)** 를 정책 계열별로 둔다. `lineage(provider, model) → H 버전`, 미등록 모델은 기본 계보로 fallback. Table 4(교차 모델 이전 +30.4% 상대)가 fallback 의 근거다. 새 계보는 해당 정책으로 RRSI 를 돌려 만든다. → 30 문서 원칙 P8.

### 4.2 "탐색 정책만 진화(Dream)" vs "하네스 전체 진화(RRSI)"

- 탐색 정책(분기·배치·정지)은 RRSI 의 𝒦 로 보면 `control_flow` 다. 두 루프가 같은 코드를 동시에 고치면 귀속이 깨진다(RRSI 의 ΔS 가 π_E 변화 때문인지 H 변화 때문인지 모름).
- **조정**: **블록 좌표 상승(block coordinate ascent)**. RRSI 실행 동안 π_E 는 고정(환경의 일부), Dream 사이클 동안 H 는 고정. π_E 파일은 RRSI proposer 의 편집 가능 경로에서 제외하고 소유권을 Dream 루프에 둔다. RRSI 의 𝒦 는 9종 그대로 유지(수식 보존). → 30 문서 P5.

### 4.3 "세션 범위 자기 수정(env 도구)" vs "전역 정규화 진화(RRSI)"

- `env` 도구는 에이전트가 자기 프롬프트·도구·스킬을 대화 중 바꾼다(세션 범위, 평가 없음). RRSI 는 전역 H 를 평가·게이트를 거쳐 바꾼다.
- **조정**: 세 층의 합성으로 본다: `실행 하네스 = H*(lineage) ⊕ 에이전트 설정(입력 x 의 일부: XGEN 노드의 지침·도구 선택) ⊕ 세션 overlay(env 도구)`. RRSI 가 진화시키는 것은 **H\* 뿐**이다. 에이전트 설정·세션 overlay 는 태스크 입력이며, H\* 는 그것들에 대해 일반적이어야 한다(RRSI 의 "낯선 태스크에서도 도움이 되는가" 리트머스). → 30 문서 P3.

### 4.4 "의미 지침은 해롭다(Dream §5.1)" vs "analyst 보고서를 proposer 에 준다(RRSI)"

- Dream-RSI 는 이력을 방향 지침으로 프롬프트에 넣으면 탐색 다양성이 줄어 성능이 떨어진다고 보고한다. RRSI 는 3-렌즈 보고서와 이력을 proposer 에 준다.
- **조정**: 층위와 대상이 다르다. Dream 의 지침은 **discovery agent 의 다음 해 방향을 강제**하는 것이고, RRSI 의 이력은 **하네스 편집 가설의 반증 기록**이다. RRSI 도 "덜 탐색된 구성요소로 돌리기(𝓔_t)"로 다양성을 *강제로 넓힌다*. 우리 규칙: (a) 하네스 진화 proposer 에는 RRSI 방식 그대로(이력+보고서+탐색 지시), (b) **런타임 탐색(π_E)이 여는 새 가지의 discovery 프롬프트에는 이력 요약 지침을 넣지 않고** B.1 처럼 "원자료를 읽고 새 메커니즘을 제안"하게 한다. 방향 다양성은 direction provider 가 구조 태그로 보장한다.

### 4.5 "재생은 공짜" vs "RRSI 평가는 비싸다"

- RRSI 의 지배 비용은 후보마다 evolve 집합 전체 × k 실행이다. Dream 은 기록이 있으면 평가가 공짜다.
- **조정(융합의 핵심 이득)**:
  1. RRSI 후보 평가가 만든 모든 시행 기록은 **그대로 Dream 의 세계**가 된다(태스크별 시행 트리). 진화는 세계 공급원이다.
  2. 정확한 경계(exact bound) 조기 종료: 후보의 남은 시행이 전부 r=1 이어도 바닥 S★−δ 에 못 미치면 평가를 멈춘다. RRSI 판정이 **바뀌지 않으므로** 무위험 절감이다(커널 최적화). 통계적 할당(Dream 이 학습하는 평가 할당 정책)은 판정을 바꿀 수 있어 별도 실험 단계로 둔다. → 30 문서 P7, 33 문서.

### 4.6 "탐색은 검증기가 있어야 한다(Dream)" vs "대부분의 대화 턴엔 검증기가 없다"

- Dream 의 s_v 는 평가기 점수다. 일반 대화 턴에는 자동 검증기가 없다.
- **조정**: 턴 안의 탐색 계층은 **검증 가능한 하위 작업**(샌드박스 코드+테스트, 실행으로 검증되는 SQL, 스키마/린트로 검증되는 문서 생성, 결정적 종료 상태가 있는 도구 작업)에서만 분기한다. 검증기 없는 턴은 퇴화 트리(가지 1개, 정련 = 일반 에이전트 루프)로 기존 동작과 같다. → 30 문서 P6.

## 5. 세 방법론의 결합 지도 (요약 그림)

```
                 ┌──────────────────────────── L1: RRSI (오프라인, 하네스 H 진화) ───────────────────────────┐
                 │  Analyze → b_t·σ_t·𝒯_t·𝒰_t·𝓑_t → P_reg(proposer) → critic(누설) → smoke → Evaluate(k)      │
                 │  → floor ∧ (Eq.7 | Eq.17) ∧ guard → argmax → S★ → 𝓛_t                                  │
                 └──────┬───────────────────────────────────────────────────────────────▲────────────────┘
                        │ 새 H*(lineage) 승격 (사람 승인)                                  │ 시행 기록 = 세계
                        ▼                                                                 │
```

## 6. 정리 — 새 프레임워크가 반드시 만족할 성질

1. **교체 가능성**: 기존 I/O 계약(11 문서)을 바이트 수준이 아니라 *의미 수준*에서 완전히 만족하고, 계약 테스트로 증명한다.
2. **편집 가능성**: 행동에 영향을 주는 모든 것이 𝒦 타입이 선언된 구성요소 하나에 속한다. 원자 편집·태그·diff 범위가 정확히 정의된다.
3. **측정 가능성**: 모든 실행에서 c(τ)(정확), 스텝 수, 유효 출력, 미제출, (있으면) r(x,τ) 가 커널에 의해 기록되고 하네스는 이를 조작할 수 없다.
4. **재생 가능성**: 모든 실행이 발견 트리로 기록되고, 탐색 결정은 prefix-only API 로만 내려져 재생으로 정확히 평가된다.
5. **정규화된 변화**: 운영 H\*·π_E\* 의 모든 변경은 RRSI 선택 게이트(누설·바닥·비용·가드)와 사람 승인을 거친다.
6. **수식 정확성**: 05 문서의 모든 수식이 순수 함수로 구현되고 검산 벡터 테스트를 통과한다.
7. **다중 공급자 유지**: 15개 provider 와 생각 조절, 루프 소유 provider 통합이 그대로 동작한다.

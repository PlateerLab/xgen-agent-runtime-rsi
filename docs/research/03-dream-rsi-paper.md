# 03. Dream-RSI 논문 분석

> 대상 논문: *Dream-RSI: Recursive Self-Improvement through Evolving Worlds* (arXiv [2609.14858](https://arxiv.org/abs/2609.14858) v1, Google · Google DeepMind · UMD · UVA). 저자 저장소 `github.com/zhengkid/Dream-RSI` 에는 2026-10-01 기준 README 만 있고 코드·재현 스크립트는 공개 전이다.
> 이 문서는 논문의 번역이 아니다. 논문이 정의한 형식과 결과를 우리 말로 요약하고 구현 관점의 해석을 붙인 분석 노트다. 원문을 그대로 옮긴 곳은 따옴표와 출처 절로 표시했다. 기호와 식 번호는 05 문서와 코드가 참조하므로 논문 표기를 따른다. 정책 API·평가자·미정의 항목의 결정은 [04](04-dream-rsi-replay-policy.md) 에 있다.

## 0. 한 줄 요약

지금까지 쌓인 발견 기록을 **재생 시뮬레이터(world)** 로 쓰면, 탐색 정책을 실제 실행 없이 오프라인에서 여러 번 평가할 수 있다. 이렇게 "꿈속에서" 고친 정책을 다시 온라인에 내보내 기록(세계)을 넓히는 재귀 루프를 탐색 계층에서 닫는다. 코딩 에이전트·모델·평가기는 고정이고 **탐색 정책 코드만** 바뀐다.

---

## 1. 문제: 탐색이 병목이다

- 자기 개선의 기본 단위는 생성 → 평가 → 피드백의 반복이고, 목표가 어려울수록 수천 번의 제안–평가에 걸친 장기 탐색이 된다. 이 규모에서는 어떤 가지를 얼마나 밀지 정하는 **탐색 조율**이 계산 효율을 좌우한다.
- 기존 시스템은 대개 고정된 수작업 탐색 전략을 쓴다. 누적 경험으로 전략이 나아지지 않는다.
- 탐색 정책을 온라인으로 최적화하려면 두 가지가 막는다. (1) 정책 하나의 품질은 그 정책이 이끈 많은 사이클이 끝나야 드러나므로 메타 피드백이 늦고 비싸다. (2) 정책 공간이 넓어 많은 후보를 시도해야 한다. 두 문제가 겹치면 온라인만으로는 루프를 닫기 어렵다.

## 2. 핵심 아이디어: 기록은 이미 시뮬레이터다 (Sec 2)

- 한 번의 온라인 탐색은 어떤 가지를 열었고, 어디서 갈렸고, 무엇을 썼고, 결과가 어땠는지를 담은 트리를 남긴다. 이 트리는 이미 관측된 부분에 대해서는 근거 있는 환경 모형이다. 모델 기반 RL(World Models, Dreamer)이 환경 모형 안에서 정책을 훈련하는 것과 같은 구도다.
- 다른 탐색 정책은 같은 트리를 다르게 순회한다(다른 가지 부분집합, 다른 우선순위, 다른 병렬 묶음, 더 이른 정지). 그 궤적의 가치는 선택된 가지의 **저장된 결과를 드러내기만** 하면 알 수 있으므로 에이전트·평가기를 다시 돌릴 필요가 없다. 비싼 온라인 실행 한 번이 실행비 0 의 off-policy 평가 수천 번으로 바뀐다(Figure 2).
- 선행 연구는 과거 기록을 프롬프트용 텍스트나 미세조정 데이터로 썼다. Dream-RSI 는 기록을 **상호작용 가능한 시뮬레이터**로 쓴다는 점이 다르고, Sec 5.1 실험이 이 차이를 검증한다.

## 3. 방법 (Sec 3)

### 3.1 구성 요소

| 구성 | 역할 | 진화 여부 |
|---|---|---|
| discovery agent | 부모 워크스페이스에서 새 시도를 만든다 | 고정 |
| evaluator | 점수·진단을 낸다 | 고정 |
| exploration policy π | 어느 노드에서 이어갈지, 몇 개를 병렬로, 언제 멈출지 정하는 **실행 가능한 코드** | **진화** |
| policy-development agent | 재생 피드백을 읽고 정책 코드를 고친다 | 고정 |

인용(Sec 3): "Only the exploration-policy code changes; the underlying models, evaluator, and execution interfaces remain fixed."

### 3.2 발견 트리와 결정 인터페이스

- 트리의 루트 r 은 초기 워크스페이스다. 루트가 아닌 노드 v 는 **1차 부모 하나**를 가지며, 그 부모의 저장 워크스페이스에서 시도가 시작된다.
- 노드는 파일시스템 스냅샷, 산출물, 평가 진단, 점수 s_v(클수록 좋음)를 기록한다.
- 정책이 볼 수 있는 관측 트리 𝒯 에서 확장 가능한 노드와 실행 가능한 배치는 다음과 같다.

```
A(𝒯)    = {r} ∪ { v ∈ 𝒯 : v is a leaf }                     적격 노드 집합 (리프는 현재 관측 트리 기준)
A(𝒯; W) = { C ⊆ A(𝒯) : |C| ≤ W }                            실행 가능 배치 집합
```

- W 는 병렬 워커 수다. 정책의 행동은 배치 C ∈ A(𝒯; W) 하나이며, 탐색을 *어디서* 잇는지와 *몇 개를* 동시에 돌리는지를 함께 정한다.
- 온라인과 재생은 **같은 결정 인터페이스**를 쓰고 배치 뒤의 전이만 다르다.

> **구조적 귀결(우리 분석)**: 리프와 루트만 확장할 수 있으므로 루트가 아닌 노드는 자식을 최대 하나 가진다. 트리는 루트에서 뻗은 여러 사슬, 즉 **branch × attempt 격자**가 된다. Appendix B 의 정책 프롬프트가 환경을 불규칙한 branch × attempt 격자로 설명하는 것과 맞는다. 구현 `src/xgen_rsi/dream/world.py` 가 이 격자 표현을 쓴다.

### 3.3 온라인 롤아웃

- 외부 반복 t = 1, 2, … 에서 정책 π_t 가 지난 기록 𝓗_{t−1} 을 참고하며 새 트리를 키운다(𝓗_0 = (), 롤아웃 중 정책 코드는 고정).
- 𝒯_t^0 = {r} 에서 시작해 라운드 k 마다 배치 `C_t^k ∈ A(𝒯_t^k; W)` 를 고르고, 배치의 각 노드에서 시도 하나씩을 병렬로 돌려 **선택된 부모마다 새 자식 하나**를 붙인다. 같은 출발점에서도 결과가 달라질 수 있으므로 전이는 확률적이다.
- 빈 배치를 고르거나 K1 라운드에 닿으면 끝난다. 최종 트리 𝒯_t 를 기록에 더한다: **𝓗_t = 𝓗_{t−1} ∪ {𝒯_t}**.

### 3.4 오프라인 평가 (재생)

- 오프라인 단계 동안 𝓗_t 는 고정이다. 정책 버전 `π_t^0, …, π_t^{M−1}`(π_t^0 = π_t)을 만들고, 각 버전을 **모든 과거 트리 𝒯_i (i = 1, …, t)** 에서 재생한다.
- 재생은 `𝒯_i^{m,0} = {r}` 에서 시작해 드러난 부분 트리 `𝒯_i^{m,k} ⊆ 𝒯_i` 만 정책에 보여 준다. 기록 트리 자체는 고정이고 정책이 바꾸는 것은 드러나는 범위뿐이다.
- 재생은 새 후보를 만들지 않고 선택된 노드의 **기록된 자식을 결정적으로** 드러낸다.

```
𝒯_i^{m,k+1} = 𝒯_i^{m,k} ∪ ⋃_{v ∈ C_i^{m,k}} Child(v; 𝒯_i, 𝒯_i^{m,k})
```

**Child 의 정의**

- v ≠ r: v 의 유일한 기록 자식(있으면). v 가 현재 리프이므로 그 자식은 아직 안 드러난 상태다.
- v = r: 아직 안 드러난 r 의 자식 중 **가장 먼저 생성된** 것. 새 가지를 하나 연다.
- 남은 기록이 없으면 `Child = ∅`.

**종료**: 빈 배치, 라운드 한계 K2, 또는 `𝒯_i^{m,k} = 𝒯_i`(전부 드러남). 종료 시 라운드 수를 `k_i^{m,★} ∈ {0, …, K2}` 로 쓴다. 각 가지는 기록된 순서로만 순회되고 기록 밖의 결과는 생기지 않는다.

### 3.5 재생 목적함수 (Eq.1)

N_i^m = |𝒯_i^{m,k_i^{m,★}}| − 1 은 드러난 **비루트** 노드 수, 즉 그 궤적이 *나타내는* 생성–평가 요청 수다. 고정 계수 β1, β2 ≥ 0 에 대해:

```
V_i^m =  max_{v ∈ 𝒯_i^{m,k★}} s_v   −   β1 · N_i^m   +   β2 · N_i^m / max{1, k_i^{m,★}}               (1)
        └──── discovery quality ────┘   └ execution cost ┘   └──── parallelism bonus ────┘
```

- 첫 항은 도달한 최고 품질, 둘째 항은 시도 수 벌점, 셋째 항은 라운드당 평균 시도 수(병렬로 묶을수록 큼)에 대한 보상이다.
- max 의 범위에 루트가 포함된다. 아무것도 드러내지 않은 재생(k★ = 0)은 N = 0, V = s_r 이다(루트 점수가 있을 때).

### 3.6 정책 개선과 선택

```
V^m = (1/t) Σ_{i=1..t} V_i^m

π_{t+1} = π_t^{m★},     m★ ∈ argmax_{m ∈ {0, …, M−1}} V^m
```

- 각 m 에서 policy-development agent 가 π_t^m 의 재생 궤적·점수·이전 피드백을 보고 코드를 고쳐 다음 버전을 만들고, 같은 t 개 세계에서 다시 평가한다.
- 후보에 현재 정책이 들어 있으므로 **V^{m★} ≥ V^0** 이다. 고정된 기록 위의 평균 재생 점수에서는 퇴보하지 않는다는 보장이며, 온라인 성능을 보장하지는 않는다.

> **표기 문제와 우리 해석**: 본문은 버전을 π_t^0..π_t^{M−1} 로 두면서 m = 0..M−1 마다 π_t^{m+1} 을 만든다고 써서, 문자 그대로면 마지막 π_t^M 이 평가 없이 남는다. 우리는 **개발 단계를 M−1 회 돌려 M 개 버전을 만들고 그 안에서 고른다**(04 문서 결정 E10).

### 3.7 전체 루프 (우리 의사코드)

```
𝓗 ← ();  π ← 수작업 초기 정책(병렬 정련)
for t = 1, 2, …:
    # 온라인: 같은 결정 인터페이스로 새 트리를 키운다
    𝒯 ← {r}
    repeat up to K1 times:
        C ← π.choose(𝒯, 𝓗)                 # C ∈ A(𝒯; W), 비면 정지
        if C is empty: break
        𝒯 ← 𝒯 ∪ { attempt(v) for v in C }   # 병렬, 부모마다 자식 하나
    𝓗 ← 𝓗 ∪ {𝒯}
    # 오프라인: 기록된 세계들에서 정책 버전을 재생·개정
    versions ← [π]
    for m in 1 .. M−1:
        versions.append(develop(versions[-1], replay_traces, scores))
    π ← argmax_{p ∈ versions} mean_i Replay(p, 𝓗[i])      # Eq.1, 결정적
```

## 4. 실험 요약 (Sec 4)

### 4.1 공통 설정

- 기준선은 **Recursive Fixed Exploration**: 같은 설정·초기화에서 탐색 정책만 고정한다. 두 방법 모두 단순 **병렬 정련**(여러 독립 워크스페이스가 각자의 이력으로 후보를 다듬음)에서 출발하므로 첫 라운드는 같다.
- 발견 비용 = 누적 discovery-agent 호출 수. 에이전트는 Gemini CLI 의 Gemini-3.1 Pro / Gemini-3.7-Flash.
- 라운드당 예산: Gemini-3.1 Pro 10 워크스페이스 × 최대 11 스텝 = 110 호출, Gemini-3.7-Flash 32 × 20 = 640 호출. 격자로 보면 B = 10, R = 10 과 B = 32, R = 19 다(04 문서 §3.5).

### 4.2 Lasso 정규화 경로 (Sec 4.1)

- 과제: 수치 정확성을 지키며 Lasso 경로 전체를 빠르게 계산하는 구현을 찾는다. 정확성 기준은 모든 k 에서 `F_k(w̃_k) ≤ F_k(w_k,sklearn) + 10⁻⁶` (`F_k(w) = (1/2n)‖y − Xw‖² + λ_k‖w‖₁`), 하나라도 어기면 0 점. 통과하면 `R_search = (Π_{i∈I} t_i)^{−1/|I|}`(타이밍 인스턴스 시간의 기하평균 역수).
- 6 개 held-out 데이터셋 평균 런타임(ms, 낮을수록 좋음): sklearn 44180.3, glmnet 13767.5, SimpleTES 3804.8(51,200 호출), Recursive Fixed 3587.1(Pro, 550 호출) / 2516.7(Flash, 3200 호출), **Dream-RSI 2931.0(Pro, 317 호출) / 2350.6(Flash, 1879 호출)**.
- 찾아낸 해법은 strong-rule screening, Cauchy–Schwarz 경계 기반 KKT 가지치기, 지연 Gram 행렬, 활성 집합 장부 등의 조합이었다. 첫 라운드 이후로는 Dream-RSI 가 더 적은 누적 계산으로 일관되게 앞섰다.

### 4.3 수학 최적화 (Sec 4.2)

Sum–Difference(`Γ(A) = log(|A+A|/|A|) / log(|A−A|/|A|)` 최대화), Circle Packing, Autocorrelation 부등식, Gemini-3.1 Pro 10 라운드. Sum-Diff 는 Dream-RSI 1.145427 로 SimpleTES(1.143975)·Recursive Fixed(1.144047)보다 높고, Circle Packing 은 모두 2.635983 으로 같으며, Autocorrelation 은 51,200 세대를 쓴 SimpleTES 가 가장 좋다. Dream-RSI 는 1k 세대 미만으로 강한 기준선과 동급 이상이었다.

### 4.4 커널 공학 (Sec 4.3)

KernelBench 4 종(성능 = 1/ms). VGG16·LayerNorm 은 비슷한 최종 성능에 세대 수 2.43×·1.79× 절감, ConvDiv·ConvMax 는 비슷한 예산에서 성능 2.09×·1.44×.

### 4.5 추가 분석 (Sec 5)

- **5.1 기록을 어떻게 쓰나**: 과거 궤적을 고수준 방향 지침으로 요약해 프롬프트에 넣는 대안을 두 방법 모두에 적용했더니(ConvDiv) 같은 예산에서 지침 없는 쪽보다 일관되게 나빴다. 병렬 장기 탐색에서 강한 의미 편향이 탐색 다양성을 줄인다는 해석이다. 기록은 읽을거리보다 **상호작용하는 시뮬레이터**로 쓸 때 더 강하다.
- **5.2 탐색 행동의 진화**(ConvDiv, Fig 6): 라운드별 최고 성능이 0.427 → 1.898 로 오르는 동안 시도 수는 110 → 50 까지 줄었다가 E4–E5 정체(1.488 → 1.499) 뒤 92 로 다시 늘었고, 이후 E6–E8 에서 1.770 → 1.898 로 더 올랐다. 탐색 노력 자체가 학습된 적응 변수라는 증거로 제시된다.

## 5. 관련 연구 위치 (Sec 6)

- **AI 주도 발견**(AlphaEvolve, OpenEvolve, ShinkaEvolve, EvoX 등): 탐색이 메타 수준 최적화 문제가 됐지만 전략 품질은 긴 롤아웃 뒤에야 드러난다.
- **자기 진화 에이전트**(가중치, Meta-Harness 같은 하네스, 컨텍스트, 스킬, rubric 진화): 대부분 객체 수준이다. Dream-RSI 는 메타 수준 최적화를 재귀적이고 off-policy 로 만든다.
- **기록 재사용**(DeltaEvolve, SwarmResearch, MLEvolve): 기록을 다음 결정의 컨텍스트로 쓰는 데 그치지 않고, 많은 대안 제어기를 싸게 평가하는 시뮬레이터로 조직한다는 점이 차이다.

## 7. XGEN 관점의 시사점

1. **탐색 정책은 하네스 안의 별도 계층이어야 한다.** 어떤 노드를 몇 개 병렬로, 언제 멈출지 정하는 코드가 에이전트 추론과 분리되어 있어야 재생·교체·진화가 가능하다.
2. **모든 실행을 트리로 기록한다.** 노드 = (부모, 스냅샷, 산출물, 진단, 점수). 선형 대화 한 턴도 사슬 하나짜리 퇴화 트리다. 오늘의 기록이 내일의 세계다.
3. **재생할 수 있는 결정만 꿈꿀 수 있다.** 가지 선택·순서·배치·정지처럼 기록으로 결과가 정해지는 결정은 재생으로 정확히 평가된다. 기록에 없는 자식을 요구하는 결정은 보상을 받지 못한다.
4. **현재 정책을 포함한 argmax 라서 재생 위에서는 퇴보하지 않는다.** 하지만 재생은 관측된 부분만 보므로 새 방향의 가치는 온라인에서만 드러난다. 정책이 새 루트를 여는 탐색 몫을 계속 유지해야 하는 이유다.
5. **의미 지침 주입보다 시뮬레이터 상호작용이 낫다**(Sec 5.1). RRSI 의 analyst 보고서처럼 기록을 텍스트로 넣는 방식과 충돌하는 것이 아니라 층위가 다르다. RRSI 는 하네스 편집 가설의 반증 기록이고, Dream-RSI 가 경고하는 것은 탐색 방향의 강제 편향이다. 조정은 30 문서.
